# 模块 03：任务生命周期与结果动作

## 1. 模块目标

让用户始终知道任务是否已提交、模型是否正在生成、成功了几张、扣了多少积分，以及下一步能做什么。界面状态必须来自真实任务和资产数据，不得用本地计时器、占位图或 Toast 冒充生成成功。

## 2. 状态机

### 2.1 合法状态

| 状态 | 含义 | 是否轮询 | 是否终态 |
| --- | --- | --- | --- |
| `queued` | 任务与 credit hold 已在同一事务创建，积分已冻结，尚未进入 provider 执行 | 是 | 否 |
| `generating` | provider 已接收或正在生成 | 是 | 否 |
| `completed` | 请求数量全部成功，资产已持久化，积分已结算 | 否 | 是 |
| `partial_success` | 至少 1 张成功，但少于请求数量 | 否 | 是 |
| `failed` | 0 张成功，错误已记录，冻结积分已释放 | 否 | 是 |

### 2.2 合法转换

```text
create → queued
queued → generating
queued → failed
generating → completed
generating → partial_success
generating → failed
```

终态不得回到 `queued` 或 `generating`。同一任务不得从 `completed` 改为 `failed`。如果持久化或结算失败，任务必须停留在可恢复的失败状态，不能向用户展示已完成。

## 3. 创建任务

用户点击生成后：

1. 客户端同步禁用按钮，阻止重复点击。
2. 调用 `POST /api/v1/image-generations`。
3. 服务端重新验证用户、模式、模型、参数、参考图与积分。
4. 服务端在同一个数据库事务中锁定可用积分、创建唯一 task 和唯一 credit hold。
5. 任一步骤失败时整个事务回滚；余额不足返回 402，task 和 hold 新增数均为 0。
6. 事务提交后返回 `taskId` 和 `redirectUrl`；后台执行只能消费这条已存在的 hold，不得再次冻结。
7. 页面 URL 切换为 `/generated?taskId=<taskId>`。
8. 页面立即显示与 `outputCount` 相同数量的任务槽位。
9. 任务进入后台执行，客户端开始轮询。

创建接口目标是快速返回任务，而不是等待模型生成完成。provider 异步执行时，创建接口 P95 不超过 2 秒。

## 4. 轮询与刷新

- `queued` 和 `generating` 每 4 秒读取一次任务详情。
- 首次打开带 `taskId` 的页面立即读取，不先等待 4 秒。
- 后台刷新不得把整页 `isLoading` 设为 true，不得每 4 秒闪回骨架。
- 只替换发生变化的任务数据和资产列表。
- 收到 `completed`、`partial_success` 或 `failed` 后立即停止 interval。
- 终态后的 5 秒内网络面板不得继续出现该 task 的周期 GET。
- 页面重新获得焦点时可以执行一次即时读取，但终态不得重新启动 interval。
- 用户离开页面不会取消服务端任务；返回后从历史或 task URL 恢复。
- 本版本不提供取消任务按钮，因为服务端没有可靠取消能力。

## 5. 运行中界面

### 5.1 参数快照

运行中生成器显示只读任务快照：模式、参考图、prompt、模型、画幅、张数和分辨率。用户不能修改一个已经提交的任务。

### 5.2 结果槽位

- 槽位数量等于任务 `outputCount`。
- 未返回的槽位显示统一 skeleton，不显示虚构进度百分比。
- 如果 provider 只能在最终响应返回全部结果，界面可以显示“正在生成 4 张”，但不能显示“已完成 2/4”。
- 只有后端确实返回逐项状态时才显示已完成数量。
- 状态使用 `aria-live="polite"` 播报，不能每 4 秒重复朗读相同文案。

### 5.3 积分说明

运行中显示“冻结 `<requestedCredits>` 积分”。冻结不等同已消费，不显示为最终扣除。

## 6. 完整成功

任务满足以下全部条件才能标记 `completed`：

- 成功资产数量等于 `outputCount`。
- 每个资产具有唯一 `outputIndex`。
- 资产已写入 `generated_assets`。
- task 的 `settledCredits` 与成功资产 `creditsCharged` 总和一致。
- 对应 credit hold 已结算且冻结余额为 0。
- task 有 `completedAt`。

界面显示：

- `已完成 N/N 张`。
- `本次扣除 <settledCredits> 积分`。
- N 张真实结果图片。
- 每张图片的下载、设为参考和更多动作。
- “继续创作”和“重新生成整组”。

## 7. 部分成功

当成功资产数量 `k` 满足 `1 ≤ k < outputCount`：

1. task 状态为 `partial_success`。
2. 成功槽位展示真实图片。
3. 失败槽位显示“生成失败，未扣积分”，不使用默认图填充。
4. 页面显示 `已完成 k/N 张`。
5. 最终扣分只等于成功资产的费用。
6. credit hold 剩余部分全部释放，冻结余额归零。
7. 成功图片可以立即下载和复用。
8. “重新生成整组”创建新的完整任务；本版本不声称只重试失败槽位。

## 8. 全部失败

0 张资产成功时：

- task 状态为 `failed`。
- `settledCredits=0`。
- credit hold 全部释放，用户可用余额回到提交前基线。
- 结果区显示与请求数量相同的失败槽位。
- 错误提示说明属于参数错误、provider 暂不可用、超时或未知错误。
- 不直接展示 provider 原始堆栈、内部 endpoint、密钥、请求体或私人参考图 URL。
- 草稿和任务快照保留。
- 提供“使用原参数重试”，调用真实 regenerate API。

## 9. 资产持久化与结算顺序

当前链路存在“先结算积分、后插入资产”的风险。本版本采用唯一的事务与补偿方案：

1. Provider 返回结果后，成功资产写入、credit hold 结算和 task 终态更新在同一个数据库事务中完成。
2. 该事务任一步失败时全部回滚；task 仍为非终态，hold 仍保持冻结，不能向 UI 展示成功。
3. 外层错误处理随后调用幂等的 `compensateGenerationFailure(taskId)`：在同一事务中释放 hold，把 task 标记为 `failed`，写入 `PERSISTENCE_FAILED` 或 `SETTLEMENT_FAILED`，保持资产数 0、`settledCredits=0`。
4. 补偿遇到暂时性数据库错误时按 100ms、500ms、1500ms 最多重试 3 次；每次使用同一 taskId，重复执行不得重复释放或写流水。
5. 如果 3 次仍失败，task 不伪造终态并触发结构化告警。为避免永久冻结，任务详情和余额读取在返回前执行 stale reconciliation：对 `queued/generating` 超过 15 分钟且 hold 仍为 `HELD` 的 task，原子标记 `failed/STALE_EXECUTION` 并释放 hold。当前函数最长 300 秒，15 分钟是明确安全阈值。
6. stale reconciliation 同样幂等；用户再次打开任务或余额后必须恢复可用积分。本版本不依赖新增 cron 或耐久队列。
7. 不允许出现“已扣积分但没有对应资产”的成功任务。
8. `settledCredits = sum(generated_assets.creditsCharged)`。
9. 任何终态对应的冻结积分必须为 0。
10. 同一 task 的结算必须幂等；重复执行不得二次扣分或重复插入资产。

## 10. 结果卡

### 10.1 默认展示

- 图片使用任务画幅，不强制裁切为正方形。
- 结果序号与 `outputIndex` 对应。
- 图片加载失败时显示资源错误，不把整个任务改为 failed。
- 桌面端 hover 和键盘 focus 都显示工具条。
- 触摸设备默认显示主操作入口，不能依赖 hover 才可发现。

### 10.2 下载

- 下载必须请求 `/api/v1/image-assets/[assetId]/download`。
- 服务端验证资产属于当前用户。
- 客户端不得直接信任或下载任意 `asset.url`。
- 下载文件名包含日期、task 短 ID 和输出序号，例如 `mm-queencard-20260712-Q9K2-01.png`。
- 触发下载后保留当前页面，不导航到 provider URL。

### 10.3 设为参考

行为见双模式生成器规格：结果写入下一轮草稿，自动切换参考图模式，满 3 张时明确选择替换槽位。

### 10.4 引用提示词

用户选择“引用提示词”时打开 Dialog：

- `覆盖当前提示词`：用任务 prompt 替换当前草稿。
- `追加到当前提示词`：在当前 prompt 后添加换行和任务 prompt。
- 关闭 Dialog：不修改。

系统不得默认覆盖用户未提交的输入。

### 10.5 重新生成

- 调用 `POST /api/v1/image-generations/[taskId]/regenerate`。
- 服务端复制原任务参数并重新验证模型是否启用、余额和当前计价。
- 新任务 `source=regenerate`，拥有新 task ID、独立 hold 和创建时间。
- 原 task、资产和结算记录保持不变。
- 新任务创建成功后页面切换到新 task URL。
- 余额不足时返回 402，不创建新 task 或 hold。

## 11. 错误分类与用户文案

| 类别 | 用户文案原则 | 主要动作 |
| --- | --- | --- |
| 401 未登录 | 登录后可继续，草稿已保存 | 登录 |
| 402 积分不足 | 显示需要和当前可用积分 | 获取积分 |
| 400 参数或模型不兼容 | 指出具体参数，不建议盲目重试 | 返回编辑 |
| Provider 暂不可用 | 明确积分已释放 | 使用原参数重试 |
| Provider 超时 | 明确任务失败或仍处理中，不能两者并存 | 查看历史或重试 |
| 部分成功 | 显示成功数量和实际扣分 | 使用成功结果或重新生成整组 |
| 资产下载失败 | 不影响任务状态 | 重试下载 |
| 未知错误 | 提供 task 短 ID，隐藏内部细节 | 重试或返回历史 |

错误区域使用 `role="alert"`；普通状态更新使用 polite live region。

## 12. 任务恢复边界

- 页面刷新后以服务端任务为准。
- 浏览器本地草稿不能把已完成任务变回可编辑任务。
- provider 回调或后台执行晚于页面离开时，用户从历史返回仍能看到终态。
- 若任务长时间停在非终态，本版本只展示“仍在处理中”及 task ID；卡死任务回收与自动退款属于耐久队列专项，不在本规格中伪装解决。
